# PHASE 36 — REPORTS (REGISTRY, STATUTORY & SCHEDULED)

## Pre-Requisite
Phases 01–35 complete (every module exposes `GET /<module>/reports/{key}?format=xlsx (job)` endpoints with `reports:export` (Round 3–4) or ad-hoc exports; Phase 26 owns the document renderer (`document_templates`, `issued_documents`, letterhead/watermark/QR); Phase 32 owns metric values and statutory *data* (`compliance_submissions`) and calls this phase's renderers for SSR/AQAR/SAR/NIRF/AISHE files; Phase 35 owns chart providers; Phase 24 delivers emails/WhatsApp; the regulatory pack (`docs/Regulatory_Pack_IN.md` §2.6) lists the statutory reports).

## Objective
One **report registry** (`app/core/reports.py`) that every module registers into — student, academic, attendance, registration, exam, results, OBE, fee, scholarship, HR/payroll, admissions, hostel, transport, library, inventory/procurement, accounting, events/facilities, communication, mentoring/grievance/discipline, placement, alumni, research/PhD, accreditation, governance, affiliation, audit — with typed parameters, visibility-aware data providers, multi-format **renderers** (xlsx, csv, pdf via WeasyPrint on institution letterhead, docx for narrative statutory formats, json) running as background jobs on the `reports` queue with signed download URLs; a **report catalogue** UI with favourites, recent runs, parameter forms generated from `params_schema`, preview and pivot/summary; an **ad-hoc report builder** over whitelisted report models (entity, columns, filters, group-by, sort, totals) that honours visibility and PII masking; **statutory reports** (AISHE DCF, NIRF data-capture per discipline, AICTE EoA data, UGC annual report, NSP scholarship returns, state fee-regulatory returns, minority/SC-ST cell returns, anti-ragging compliance, RTI annual return, UGC PhD-awarded return, placement statistics in NIRF format, affiliated-colleges list, GST reports) rendered from Phase 32 metric values + module providers with a review/sign-off step and file registration in `issued_documents`; **scheduled reports** (cron-like cadence, recipients by role/user, formats, delivery by email/WhatsApp/in-app with signed links, run history); print-ready registers (admission register, attendance register, fee register, results register, script custody register, degree register); and report access auditing.

## Feature keys
`reports.core` (on, starter: registry, catalogue, runs, registers, builder), `reports.scheduled` (on, standard; depends `reports.core`), `reports.statutory` (off, professional; depends `reports.core` — statutory renderers/sign-off; Phase 32 exports call them when enabled).

## Visibility rules
Every report provider queries through the owning module's repository with the caller's principal, so a report never shows rows the caller could not list: an HOD's "Attendance register" contains department sections only; a faculty member's "Marks sheet" only own offerings; a college admin's "Fee register" only the college. Parameters that select scope (`college_id`, `department_id`, `program_id`, `batch_id`) are validated against the caller's scopes (narrowed silently, like `?scope=`). PII columns are masked unless `<module>:view_pii`; statutory reports contain aggregates only.

## 36.1 Database tables
No new tables. Report runs are `background_jobs` rows (job type `report.run`; params = report key + parameters + format; the result URL and a result JSON with row counts/checksums); schedules, favourites and saved builder definitions live in `institution_settings` (category `reports`: keys for schedules, builder models and saved reports) and in `users` (preferences → favourites/recent); statutory outputs are registered in `issued_documents` (template type "statutory report", entity type "compliance submission") and linked from `compliance_submissions` (§29); data comes from every module's tables through registered providers, `metric_values` (§29) for statutory figures, `institution_profile` (§2) for letterhead, `document_templates` (§25) for print layouts, `message_logs` (§23) for delivery evidence, `audit_logs` (§6) for access auditing. Expected delta migration: none.

## 36.5 Repository
`report_repository.py` (`module="reports"`; runs = `BackgroundJob` filtered by `job_type='report.run'` with self predicate `requested_by` and `reports:view_all` for admins; settings-backed schedules/saved reports/builder models via `institution_repository`; favourites via `user_repository.preferences`), `report_model_repository.py` (executes builder definitions by composing SQLAlchemy selects over the whitelisted `ReportModel` (never raw SQL from clients), always through the base entity's `BaseRepository.visible_to(principal, module)`, applying `mask_pii` on `pii` columns unless `<module>:view_pii`, server-side `LIMIT` ≤ `reports.max_rows`, statement timeout 60 s, streaming cursor for file rendering), `statutory_repository.py` (reads `metric_values`/`compliance_submissions` (Phase 32) and module providers; writes `issued_documents` rows for generated files and links them on `compliance_submissions`).

## 36.6 Services
- `report_service.py` (`reports.core`)
  1. Catalogue for the principal = `REPORT_REGISTRY` filtered by permission + feature; grouped by category; favourites and last run merged; `params_schema` returned for form generation (pickers resolve to scoped endpoints: college/department/program/batch/term/staff).
  2. `run(principal, request)`: validate params (JSON Schema) and scope params against `meta.visibility` (narrow silently); `inline_preview` runs the provider with `LIMIT max_inline_rows` synchronously; otherwise enqueue `report.run` on the `reports` queue → provider streams rows → renderer (`xlsx` via openpyxl write-only mode with header styles/freeze panes/number formats (paise → ₹ columns), `csv` UTF-8 BOM, `pdf` via Phase 26 renderer with the report layout template (letterhead, page numbers, generated-by/at, watermark "DRAFT" when `params.draft`), `docx` via python-docx for narrative statutory formats, `json`) → file service (per-tenant prefix, `reports.retention_days`) → `result_url` signed; checksum (sha256) and row count stored in `background_jobs.result`; `log_audit("reports","run")` with key/params; notify requester `reports.ready`/`reports.failed` (+ optional deliver_to); cancellation supported between chunks.
  3. Registers (print-ready, `layout='ledger'`): admission register (Phase 08), attendance register per offering/month (Phase 11), fee collection/day-book register (Phase 12), results register per session/program (Phase 15), script custody register (Phase 14), degree register (Phase 18), certificates serial register (Phase 26), leave register (Phase 06), stock/asset registers (Phase 22), library issue register (Phase 19), hostel occupancy register (Phase 20), visitor register (Phase 25), grievance register (Phase 27) — each a registered report with the ledger template and page-wise totals.
  4. Retro-registration: every Round 1–4 `/…/reports/{key}` endpoint becomes a `ReportDef` (same key, same permission/feature); the old routes stay as thin aliases calling `run` so existing verification scripts keep passing.
  5. Access log page: `audit_logs` rows for `reports` (run/download) with key/params/user/time; report downloads via signed URL are logged by the file service (`documents.downloaded` pattern from Phase 26).
- `builder_service.py` (`reports.core`): `ReportModel` whitelist per module (students, enrolments, attendance summaries, registrations, marks, results, fee invoices/payments, staff, leaves, payroll, applicants, hostel allocations, library issues, assets, placements, publications, scholars, grievances, events, service requests …) each with allowed columns/joins/filters and PII flags; `preview(definition)` (≤ 200 rows) and `run(definition, format)` (job); saved reports (private or shared with roles) stored in `institution_settings['reports.saved_reports']` with owner; group-by/aggregates (count/sum/avg/min/max) and totals; guard rails: only whitelisted columns, max 3 joins, `reports:manage` to share with roles, masked PII unless `view_pii`, all rows through visibility.
- `statutory_service.py` (`reports.statutory`)
  1. Definitions from the regulatory pack (`pack.statutory_reports`): each `StatutoryCode` has a period type, sections, data providers (Phase 32 `metric_values` by key/period + module providers for row-level tables, e.g. AISHE student tables by category/gender/state from Phase 07, staff tables from Phase 06, finance from Phase 23; NIRF placement/higher-studies rows from Phase 28, PhD from Phase 31, research from Phase 30; NSP returns from Phase 12; RTI annual from Phase 33; affiliated colleges from Phase 34; GST from Phase 12/23), validations (section totals equal, mandatory fields present, consistency with Phase 32 `consistency_service` results) and renderers (xlsx/csv DCF layouts, docx narratives, pdf cover with sign-off block).
  2. `generate(code, period)` (job): build payload → validate → render files → register `issued_documents` → create/update the Phase 32 `compliance_submissions` row (`status='generated'`, payload preview) → status `generated`; `request_review` → notifications to `signoff_roles`; `sign_off` by each role (order-free; all required) → `signed_off` (files locked; regenerating creates a new version row and revokes the old document); Phase 32 `submitted` marking stays in Phase 32; `reopen` with reason before submission only.
  3. Diff vs previous period (per section), export pack (zip of all formats + validation report), calendar of due dates from the pack (AISHE, NIRF, AICTE, UGC, NSP, RTI) → reminders (Phase 32 Beat also reminds; this phase supplies the file generation).
- `schedule_service.py` (`reports.scheduled`): CRUD schedules (report key or saved report, params, format, cadence with `at` in institution TZ within `schedule_hours_allowed`, recipients by role (resolved at run time within their scope — each recipient gets the report **as that recipient** so an HOD receives department rows) or explicit users/emails (explicit emails receive only non-PII reports; enforced), channels email/WhatsApp/in-app); `next_run_at` computation (daily/weekly/monthly/termly (on term status changes) /cron expression validated); Beat `reports.schedules_tick` (every 5 min: due schedules → one `report.run` job per recipient scope → deliver via Phase 24 with signed link (attachments only when ≤ 10 MB) → history in `background_jobs.result.delivery`); pause on 3 consecutive failures with notification to the owner; owner = creator; `reports:manage` edits others'.
- `render_service.py`: shared renderers used by Phase 32 exports and Phase 36 (`render_xlsx(sheets)`, `render_pdf(template, context)`, `render_docx(sections)`, `render_csv`), theming from `institution_profile` (logo, head signature block), pagination, bilingual headers when the pack supplies them, number/date formatting per institution locale.
