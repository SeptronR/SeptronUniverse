# PHASE 29 — ALUMNI, ENDOWMENTS & FUNDRAISING

## Pre-Requisite
Phases 01–18, 25, 26 complete (students → `graduated` transitions and `student.graduated` events from Phase 18, events module, document renderer for 80G receipts, payments gateway from Phase 12, communication core). Phase 28 (placement offers) seeds first employment; Phase 23 (accounting) consumes donation postings; Phase 27 (surveys) runs alumni surveys; Phase 32 reads alumni metrics.

## Objective
Lifelong relationship with graduates: **alumni profiles** auto-created on graduation (and bulk-imported for legacy batches) with self-service claiming/verification, employment history, consent-based **directory** and search, mentorship/recruiting willingness, **alumni events** (reunions, webinars, meets) on the Phase 25 events engine with registrations and fees, **alumni jobs board** (moderated posts, apply links), **fundraising campaigns** with goals/progress and **donations** (online via gateway, offline with receipts, corporate/individual/alumni donors, **80G receipts** with PAN capture, annual 10BD-style statements), endowment/restricted-fund tagging to Phase 23, alumni **certificate/transcript requests** (Phase 26/16 reuse via alumni identity), engagement scoring and chapters — with self (my profile/donations/requests) vs alumni coordinator (all) views.

## Feature keys
`alumni.core`, `alumni.portal` (on, standard); `alumni.jobs_board` (off, standard; depends `alumni.portal`); `alumni.fundraising` (off, professional; depends `alumni.core`); `alumni.donations_80g` (off, professional; depends `alumni.fundraising`); `portals.alumni` (Phase 39 shell).

## 29.6 Services
- `profile_service.py` (`alumni.core`, `alumni.portal`)
  1. Auto-create on `student.graduated` (Phase 18) with `graduation_year`, `program_id`, contact from student record, first employment from an accepted `placement_offers` row (Phase 28) → `alumni_employment_history(is_current)`; `alumni` role granted to the student's user on graduation (portal login continues with the same account); legacy import (CSV: registration number, name, year, programme, contacts) creates `students(status='alumni')` stubs when no student row exists (flagged `legacy`).
  2. Claim & verification: unclaimed legacy profiles claimed via registration number + graduation year + OTP on the email/phone on record (or coordinator verification with document upload); duplicates merged (audit, keeps ids mapping); `is_verified` gates directory listing and job posting.
  3. Consent (DPDP): `consent_contact`, per-field directory consent, `willing_to_mentor/recruit`; contact requests from other alumni/students routed as in-app/email relay without exposing contact details unless consented; data export/erasure via Phase 01 DSR.
  4. Employment history (current + past), higher studies (from Phase 28 opt-out data or self), LinkedIn link; profile completeness; annual "update your profile" campaign (Phase 24) with tokenised link.
  5. Engagement score (weights) recomputed nightly; chapters (city/country groups) as saved directory filters + chapter leads; alumni membership card (Phase 26 template).
- `directory_service.py`: search with facets (batch, programme, city, company), projection per consent, mentor/recruiter finder for placement officer (`willing_to_recruit`), department view for HOD (consented), students access when `directory_open_to_students`; rate-limited; export only for coordinator (audited, masked for auditor).
- `event_service.py`: alumni events are Phase 25 `events(event_type='alumni')` wrapped by `alumni_events` (type, registrations count sync); invitations to batches/chapters (Phase 24 segment on alumni), registrations/fees via Phase 25 (`event_registration` linkage), attendance, photos; webinar links; feeds NAAC 5.4.1 (alumni engagement) evidence.
- `jobs_service.py` (`alumni.jobs_board`): posts by verified alumni (or coordinator), moderation queue (`jobs_moderation`), expiry, apply link tracking (click counts), visibility to alumni and (setting) final-year students; placement officer can convert a post into a Phase 28 company/drive lead.
- `fundraising_service.py` (`alumni.fundraising`, `alumni.donations_80g`)
  1. Campaigns with goal/progress, purpose, period, restricted-fund flag → Phase 23 ledger mapping (restricted fund account) and `budget`/grant-style reporting; milestones notifications (25/50/75/100 %).
  2. Donations: **online** via `PaymentGateway` (Phase 12 online flow with `payer_type='alumni'|'individual'|'company'`, `source_type='donation'`, min amount) → webhook confirms → donation row; **offline** (bank transfer/cheque/cash/UPI) recorded by coordinator/accountant with reference; anonymous donations allowed (donor display hidden); `raised_paise` updated under `FOR UPDATE`; thank-you notification; posting event `alumni.donation_received` → Phase 23 income (general or restricted fund).
  3. 80G receipts (`alumni.donations_80g`): PAN captured (encrypted; required above threshold), receipt number from `80g:{fy}` sequence, Phase 26 template `donation_receipt_80g` with institution 80G registration details/signatory → `receipt_document_id`; corrections via reissue; **Form 10BD-style annual statement** export (donor-wise, PAN, amount, mode) for the financial year; donation register for statutory audit; refunds via Phase 12 (rare, audited).
  4. Donor CRM-lite: donor page (all donations, receipts, campaigns), corporate donors with CSR references, pledges (setting) with reminders.
- `requests_bridge_service.py`: alumni transcript/certificate requests reuse Phase 16/26 with alumni identity verification (verified profile) and alumni fee rules; convocation-in-absentia and degree download reuse Phase 18 `/degrees/me`.
- `stats_service.py`: verified %, employed %, higher studies %, geographic spread, donations by campaign/year, event participation, mentors count → Phase 32 (`alumni.*` metrics for NAAC 5.4.x) and Phase 35 dashboards.
