# PHASE 38 — SUPER ADMIN & SAAS OPERATIONS

## Pre-Requisite
Phases 01–37 complete (Phase 02 shipped the feature registry/flags, the super-admin **Features** tab and matrix, entitlements (`subscription_plans`, `institution_subscriptions`, `usage_meters` monthly job), impersonation with audit and the `support_agent` role; Phase 03 shipped institution onboarding (`onboard`) and suspend/activate; Phase 01 shipped read-only mode, help articles and feedback endpoints; Phase 37 shipped audit/integrity and settings; Phase 24 meters SMS/WhatsApp/AI usage; Phase 41 supplies adapter health probes (this phase renders the platform health page from `integration_health_checks` already written by the Phase 01 Beat and Phase 24 probes); Phase 40 provides the marketing site forms that create `pending_registrations`/`demo_requests`).

## Objective
The **platform operator's console** and the SaaS business layer: institution lifecycle (pending → trial/active → grace → suspended → archived; onboarding wizard by institution type with templates; tenant **export**, **reset** (demo) and **erasure**), **plans & subscriptions** (tiers, limits, enabled features, trials, upgrades/downgrades with proration, renewals, grace, invoices with GST, payments through the platform gateway or manual references, dunning), **usage metering** (students/staff/storage/SMS/WhatsApp/email/API calls/AI tokens per month with overage alerts and per-tenant caps), **impersonation** oversight, **support tickets** (tenant admins raise; super admin/support agents triage, reply, link diagnostics; SLA), **help centre** authoring (platform + institution articles, contextual slugs) and **in-app feedback** triage, **platform announcements** (audience by plan/type/institution; banner + in-app + email), **integration health** across tenants with outage banners, **read-only/maintenance** windows (platform/tenant, scheduled), **platform settings** (billing, rates, defaults, min app versions, captcha, keys), **self-serve registration** and **demo requests** (provisioning job, expiry, CRM-lite), the **demo tenant nightly reset**, the **super-admin audit** (all platform actions incl. support reads) and a platform dashboard (tenants by status/plan/type, MRR/ARR, usage, health, tickets, chain-integrity status).

## Feature keys
`platform.read_only_mode`, `platform.help_center`, `platform.in_app_feedback` (Phase 01, starter, on); `data.export_portability` (on, standard; tenant export lives here, user export in Phase 43 DSR); no institution-facing keys are added — super-admin features are platform-level and gated by `is_super_admin`/`support_agent` role, not feature flags. Plan tiers `starter | standard | professional | university` per `docs/Feature_Flags.md` §3.

## 38.6 Services
- `institution_admin_service.py` (super admin)
  1. Lifecycle: `pending` (created by self-serve registration or wizard without activation) → `activate` (subscription required) → `suspend` (reason; users' logins → 403 `INSTITUTION_SUSPENDED`; Beat jobs skip; webhooks paused; public website shows a maintenance page) → `activate`; `archive` (after export; read-only for platform, hidden from tenant users) → `unarchive`; `erase` (after archive + retention; job anonymises/deletes per Phase 37 manifests; irreversible, requires typed slug + MFA re-auth + second super admin approval when `platform_settings['danger.four_eyes']`).
  2. Onboarding wizard by type: templates decide defaults — **university**: `institution.multi_college` on, `affiliation.*` enabled by plan, exam authority university, college scopes; **autonomous**: single main college, exam authority autonomous; **affiliated**: parent university name, exam authority university, Phase 34 college role; **standalone**: minimal; steps: institution → admin → plan/trial → pack → template → features preview (diff vs plan) → optional demo data → custom domain (Phase 40) → done; runs Phase 03 `onboard` + `feature_service.apply_plan_defaults` + subscription creation; provisioning job with progress and a summary email with credentials link (never the password).
  3. Tenant export (job): dump every tenant table (RLS-scoped) to JSON/CSV per table + files manifest (signed URLs or bundled zip when ≤ 5 GB) + `Database_Schema.sql` version + checksums → encrypted zip (password emailed separately) in `platform/exports/{institution}/{ts}/`; requestable by institution admins (`data.export_portability`) as well as super admin; expiry 7 days; audit.
  4. Reset (demo tenants): job drops tenant rows (order by FK graph, RLS off under platform role), re-runs `seed_demo_institution.py --type <type> --all`, restores flags; nightly Beat for `demo.institution_slugs`; production reset blocked unless `danger.allow_prod_reset` + typed slug.
  5. Detail page data: profile, subscription + invoices, usage, flags summary (Phase 02), connections health, tickets, impersonations, chain-integrity status (Phase 37 digests), last logins, storage.
- `subscription_service.py`
  1. Plans CRUD (super admin): `enabled_features` validated against the registry; deactivating a plan keeps existing subscriptions; plan change preview lists features that would be disabled (with dependants).
  2. Assign/renew/change: trial (`trial_days`) → `active` on payment or manual activation; `change` now → proration credit/charge (`billing.proration`) → invoice; next-cycle change scheduled; downgrades that exceed new limits (students/staff/storage) → 409 `RULE_VIOLATION` with counts; on change → `feature_service.apply_plan_defaults` preserving overrides + `subscription.changed` (Phase 02 entitlements cache).
  3. Invoices per period: number from platform sequence `inv:{fy}`; GST from `billing.gst_pct` (institution `gstin` printed); PDF via Phase 36 renderer (platform letterhead); statuses `issued → paid | overdue`; payment via platform `PaymentGateway` connection (Phase 41 adapter; order → webhook → `paid`) or manual `payment_ref`; dunning: reminders at due−7/due/due+7 → `grace` at `grace_days` → `expired` (logins allowed read-only; writes 403 `SUBSCRIPTION_EXPIRED`) → reactivate on payment; cancellation at period end.
  4. Tenant-facing: `GET /billing/subscription`, invoices list/download, pay online, usage vs limits (Phase 02 entitlements page extended).
- `usage_service.py`: monthly meter job (Phase 02 `usage.meter` moved here, run 1st of month + daily incremental for the current month), cost computation with `usage.rates`, caps (`usage.caps` per tenant; API cap enforced by the rate limiter with 429 `RATE_LIMITED` and a tenant banner; SMS/WhatsApp caps enforced by Phase 24 credits → `CREDITS_INSUFFICIENT`), overage alerts at `overage_alert_pct` and 100 % to institution admin + super admin, platform totals, export csv; usage also feeds `mv_kpi_daily`-style platform read model (Redis) for the dashboard.
- `impersonation_service.py` (Phase 02 extended): list/filter across tenants, writes count per session (from `audit_logs.impersonator_id`), force-stop (revokes the impersonation session), policy: reason mandatory, max duration 60 min (auto-stop), `support_agent` read-only; tenant admins see active impersonations on their tenant (Phase 37 platform actions) and receive `platform.impersonation_started` (setting `saas.notify_impersonation` default on).
- `support_service.py`
  1. Tickets raised by tenant admins (portal `/admin/support`) or created by platform staff on behalf; `ticket_number`; SLA from priority; assignment (auto to on-call from `platform_settings['support.oncall']`), replies (tenant-visible vs internal notes), attachments (file service, platform prefix), status machine `open → in_progress → waiting (on tenant) → resolved → closed` (auto-close 5 days after resolved; tenant reopen within 14 days), CSAT rating on close, links: impersonate target (opens Phase 02 flow with the ticket as reason), diagnostics snapshot (versions, feature flags diff, last errors from Sentry link, failing connections), related feedback entries; SLA breach → escalation to super admin; email/in-app notifications both ways (tenant replies by email are not ingested — link to portal).
  2. Help centre: platform articles (markdown, module, audience by roles/portals, publish), institution articles (institution admins; override platform slug by same slug), contextual lookup by route slug (`help:<route>`), search, "was this helpful" counters (Redis), export/import of platform articles (json) for versioning in the repo (`docs/help/*.md` → seed).
  3. Feedback triage: board by status/category/rating; respond to the user (notification `feedback.responded`); convert to ticket; export; screenshot storage retention 90 days.
- `announcement_service.py` (platform): audience resolution (all / plan / institution type / institution ids / roles), channels banner (client polls `GET /platform/announcements/active` every 5 min or via `/auth/me`), in-app notification and email through Phase 24 (platform sender), schedule window, dismiss per user; used for release notes, maintenance notices and incident updates; institution announcements remain Phase 04/24.
- `health_service.py` (platform view): latest health per connection across tenants (Phase 01 Beat + Phase 24 probes write `integration_health_checks`), grouping by provider to detect provider-wide outages (≥ 50 % failing → outage banner to affected tenants + status page (Phase 44)), retry now (enqueue probe), disable connection (tenant notified), history chart per connection; dead-letter counts (outbox/webhooks) per tenant with retry links (Phase 41 UI).
- `read_only_service.py` (Phase 01 extended): scheduled windows (platform or tenant) with reason and notice lead time (announcement auto-created), current/upcoming list, cancel; exam-day windows requested by tenant admins (`settings:manage`) for their own tenant.
- `platform_settings_service.py`: typed platform keys (Phase 37 catalogue `scope=platform`), secrets never returned (`***`), min app versions & force update (feeds `/mobile/config` and `/public/config`), captcha provider keys, billing profile, support on-call, danger flags; every change audited.
- `registration_service.py` (self-serve, Phase 40 forms): `POST /public/registrations` (captcha + rate limit) → `pending` + verification email (signed link) → `verified` → plan choice → payment (gateway order; free trial skips) → `paid` → provisioning job (`institution_admin_service.onboard` with template by type) → `provisioned` (welcome email with login link) | `failed` (retry by super admin) ; `expired` after `registration.expiry_hours`; slug uniqueness/reserved words; duplicate email guard; super admin list/actions; `demo_requests`: form → `new` → CRM-lite statuses with notes; email notifications to platform sales (`platform_settings['sales.email']`).
- `platform_dashboard_service.py`: tenants by status/plan/type, MRR/ARR (active subscriptions normalised monthly), trials ending in 7 days, overdue invoices, top usage/overage tenants, failing connections/outages, tickets open by priority with SLA breaches, chain breaks (Phase 37), dead letters, active read-only windows, recent platform actions; cached 5 min.
