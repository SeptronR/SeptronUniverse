# PHASE 37 — AUDIT LOGS, SECURITY EVENTS & SETTINGS

## Pre-Requisite
Phases 01–36 complete (Phase 01 shipped `core/audit.py` (`log_audit` + middleware fallback), the partitioned hash-chained `audit_logs` table and partition maintenance; Phase 02 shipped sessions/login history/impersonation/MFA/IP allow-lists and PII masking that records `view_pii` reads; Phase 03 shipped the typed settings template, categories, cache and the `/admin/settings` page; every later phase added settings keys and audit calls; Phase 14–16 write QP print logs, script custody, moderation, decode and publication events; Phase 36 provides renderers for exports).

## Objective
Make the platform's trail **visible, verifiable and governable**: an **audit explorer** (filters by module/action/user/record/date/impersonation, record timeline with before/after diff viewer, "who viewed" for confidential reads, export), **hash-chain verification** (per institution, per period; first broken link reported; scheduled integrity checks; signed daily chain digests archived to cold storage), **exam audit views** for COE/auditor (per session: marks entry/verification/lock/correction trail, question-paper print log, script custody chain, valuation assignment and discrepancy actions, moderation and grace decisions, decode events with IP, result runs and version history, publication and reval/malpractice decisions), a **security events** console (login failures/lockouts, MFA changes, session revokes, password resets, IP allow-list edits, API-key use, impersonation sessions, exports and bulk downloads, PII unmasks) with anomaly alerts, the **settings catalogue** completed across all modules (searchable, typed, college-level overrides with effective-value resolution, change history, import/export, environment/plan-locked keys, validation and dependency hints), **retention & archival policies** (per data class: logs, notifications, messages, events, visitor PII, previews, job files; archival of closed years and cold partitions with manifests; legal-hold exceptions), platform/tenant **feature-flag change log** and **super-admin action audit** surfaced to institution admins where it affects their tenant.

## Feature keys
`core.audit_logs` and `core.settings` (core, registered in Phase 01/03 — always on); `security.session_management` (Phase 02) gates the sessions/login-history views; `privacy.dpdp_consent`/`privacy.data_subject_requests` gate the privacy panels; no new keys (retention/archival are core operations controlled by settings).

## 37.6 Services
- `audit_service.py` (`core.audit_logs`)
  1. Explorer queries with mandatory date bounds (default last 30 days, max 366 days per query; exports beyond via job), free-text `q` over `record_label`/summary (summary rendered from `module:action` templates registered per module, e.g. `fees:collect` → "Collected ₹{amount} receipt {number}"), impersonation filter, masking of `old_values/new_values` by the record module's `view_pii`; record timeline merges `audit_logs` with domain events (`domain_events` by `aggregate_id`) and workflow steps for the record; "who viewed" for confidential record types (`students` PII, `health_visits`, `grievances`, `staff` salary/bank, `answer_scripts` decode).
  2. **Chain verification**: recompute `hash` for each row (`prev_hash || module || action || record_id || new_values || occurred_at`) in order per institution; report `ok`/first broken row; daily Beat computes the day's chain digest (last hash + row count) → signed with `audit.digest_signing_key_id` (platform key) → stored + written to cold storage (`{institution}/audit-digests/{date}.json`) → tamper evidence independent of the DB; `verify_chain` endpoint (`audit_logs:verify_chain`) compares stored digests with recomputation; broken chain → `audit.chain_broken` to institution admin + super admin (Phase 38 platform alert), read-only recommendation banner.
  3. Exports (job): filtered rows to csv/xlsx/json (masked unless `view_pii`), themselves audited (`audit_logs:export`).
  4. Completeness guard: `scripts/check_audit_coverage.py` — every service method decorated `@mutation` (or every non-GET route) calls `log_audit` or is listed in `AUDIT_EXEMPT`; CI green.
- `exam_audit_service.py` (`exams:audit`): per exam session sections — **marks**: `internal_marks` entry/edit/submit/verify/lock and `marks_change_requests` decisions; **qp_print**: `question_paper_print_log` (who/when/copies/watermark); **custody**: `script_custody_log` chain per bundle with gaps flagged; **valuation**: `valuation_assignments` (assigned/reassigned/rounds), discrepancy actions, `script_valuations` submits (evaluators by dummy id); **moderation**: `moderation_actions` with approver and delta; **decode**: `audit_logs(action='decode')` with IP and allow-list match; **runs**: `result_processing_runs` with `config_snapshot` hash and anomaly counts; **publication**: `result_publications` and result version supersessions (`student_course_results`/`student_term_results` version chains); **post_result**: `reval_requests` and `malpractice_cases` decisions; summary card (counts, open gaps, time from last exam to publication); export as the "exam audit report" (Phase 36 registered report `exams.audit_trail`) for peer teams/auditors.
- `security_service.py` (`security.session_management`, `security:view_all`)
  1. Security events console (login failures/lockouts by identifier/IP, MFA enrol/disable, password resets, session revocations, refresh reuse detections, IP allow-list changes, API-key creation/use/rate-limit hits, webhook secret rotations, impersonation start/stop with reason, bulk exports/downloads, PII unmask bursts, feature toggles, settings changes in `security` category).
  2. Anomaly rules (settings) evaluated by Beat every 5 min over the last window → `AnomalyAlert` (Redis + audit row) → `audit.anomaly` notification to `audit.alert_recipients`; acknowledge with note; recommended actions (revoke sessions, disable API key, lock user — links to Phase 02 endpoints).
  3. Admin session management: list sessions across users (masked IP, device, last seen), revoke one/all for a user (e.g. departing staff), force MFA re-enrolment; login history per user.
- `settings_service.py` (`core.settings`; extends Phase 03)
  1. Catalogue: all keys with metadata; search; grouped by category; `scope` decides where the key may be set (platform-only keys read-only for tenants; `college` keys overridable per college); `locked_by: plan` keys show the plan reason (Phase 38 entitlements); `requires_restart`/cache notes.
  2. Effective value resolution `college → institution → platform default` with source badge; `PUT /settings` validates type/enum/range/dependencies (e.g. `fees.gst_enabled` requires `institutions.gstin`), rejects locked keys (409 `RULE_VIOLATION`), writes audit with reason (sensitive categories `security`, `privacy`, `fees`, `exams` require `reason`) and emits `settings.changed` (cache invalidation; some keys fan out `settings.changed_sensitive` notification to principal).
  3. History from `audit_logs` (`module='settings'`) per key; import/export JSON (dry-run report; locked/invalid keys skipped); reset key to default; college override management (set/clear per college); "what changed since" diff between dates.
- `retention_service.py`
  1. Policies per data class from `privacy.retention` (institution may shorten, never lengthen beyond platform maximums; `legal_hold` entries exempt rows: by batch/enrolment/exam session/date range); preview counts before running.
  2. Purge jobs (Beat daily 03:30): `login_history`, `notifications`, `message_logs` (content only — delivery metadata kept 1 more year), `domain_events` (dispatched → payload archived to S3 then deleted), `webhook_deliveries`, job/report/preview files (file service), `visitor_passes` PII (Phase 25 job consolidated here), `vehicle_gps_logs` partitions; every purge writes an audit row with counts and a manifest.
  3. Archival (`archive_year.py` scheduled + on-demand): closed academic years → cold partitions of `student_class_attendance`, `message_logs`, old `audit_logs` partitions (after `audit_logs_archive_after_years`) → `DETACH`, export to Parquet/CSV with sha256 manifest to `{institution}/archive/{class}/{period}/`, then drop; audit rows are **never** deleted before archival and their digests remain verifiable; restore job (super admin) re-attaches from the archive for audits; manifests browsable.
  4. DSR support: erasure requests (Phase 43 completes DPDP flows) call `retention_service.erase(user)` which anonymises PII in non-record tables and records the manifest; academic records retained per policy with a note.
- `feature_change_service.py`: institution-visible log of `feature_flag_changes` (who/when/reason/old/new) and super-admin actions affecting the tenant (`audit_logs` rows with `institution_id` = tenant and platform actor), surfaced on the institution audit page (read-only).
