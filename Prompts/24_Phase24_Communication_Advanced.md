# PHASE 24 — COMMUNICATION ADVANCED

## Pre-Requisite
Phase 04 complete (templates, channels + adapters, DLT/WhatsApp registries, preferences, message logs, announcements with acknowledgement, notification centre), Phases 07/06 (students, guardians, staff for audiences), Phase 12 (dues for segments and bot answers), Phase 11 (attendance for bot answers). Phases 14–16 enrich the assistant tools when present (exam schedule, results).

## Objective
The outbound and conversational layer on top of the communication core: **audience segments** built from live data (programme/batch/department/hostel/route/dues/attendance/roles), **bulk campaigns** across SMS/WhatsApp/email/push/in-app with DLT/WhatsApp template compliance, throttling, **scheduled sends**, cost estimation and per-tenant credit metering; announcement analytics (read/ack funnels, reminders to non-acknowledgers); **emergency broadcast** (all channels, all audiences, bypass quiet hours, incident log); **WhatsApp bot flows** (menu-driven: attendance, dues, timetable, results, hall ticket, out-pass status, fee receipt, complaints) with session state and idempotent webhook processing; the **AI assistant** (higher-ed tools over the same read APIs, permission- and visibility-aware, with audit and opt-in) for web/mobile/WhatsApp; a **channel simulator** for demos and QA; delivery analytics and provider health — with self (my messages/preferences) vs communication officer (all) views.

## Feature keys
`comms.bulk_campaigns` (on, standard; depends `comms.sms`), `comms.scheduled_sends` (on, standard), `comms.announcement_ack` (Phase 04; analytics here), `comms.emergency_broadcast` (off, standard), `comms.whatsapp_bot` (off, professional; depends `comms.whatsapp`), `comms.ai_assistant` (off, professional), `comms.whatsapp` (off, standard); simulator is always available in `APP_ENV != production` and behind `platform.simulator` setting elsewhere.

## 24.6 Services
- `segment_service.py`: rule compiler (`field` catalogue: programme/batch/section/department/college/hostel/route/role/gender/category/status/dues/attendance/term/custom list; ops `eq|in|between|gte|lte|is_null`) → recipient set of `users` with channel reachability (verified phone/email, WhatsApp opt-in, device token); preview with counts and samples; saved segments (name, rules, owner, shared); **visibility applied at compile time** (HOD → own department only; college admin → own college); deduplication across persons (guardian receives once even for two wards; setting `notify_guardians` on campaigns).
- `campaign_service.py` (`comms.bulk_campaigns`, `comms.scheduled_sends`)
  1. Create with channels and content: SMS requires a DLT-registered template match (`dlt_templates` variables), WhatsApp requires an approved `whatsapp_templates` name for outbound-initiated messages (free text only inside a 24 h session), email HTML sanitised, push title/body limits; compliance check returns blocking errors.
  2. Cost estimate = recipients × per-channel rate (`platform_settings['comms.rates']`) vs credits (`usage_meters` SMS/WhatsApp balance from Phase 38 entitlements) → 409 `CREDITS_INSUFFICIENT` on send; above `campaign_approval_threshold_recipients` → `pending_approval` (`communication:approve`).
  3. Schedule (`scheduled_at`, institution TZ) → Beat picks due campaigns; `send_now`; sending as a job with throttling per channel (`throttle_per_minute`), per-recipient preference/quiet-hours handling (non-emergency defers into next allowed window, `respect_quiet_hours`), unsubscribe honoured for marketing category, batch writes to `message_logs` with `campaign_id`, progress in `background_jobs` (pause/resume/cancel), retries of failed with backoff and `retry_failed` action; provider webhooks (delivery/read) update logs (Phase 04 adapters); completion notification with report.
  4. Department campaigns by HOD/faculty (`communication:send` scope) limited to own audiences and in-app/email/push unless SMS granted; audit every send.
- `announcement_analytics_service.py` (`comms.announcement_ack`): audience size (from rules), read/ack counts, pending list (visible per scope), funnel over time, reminder campaign to non-acknowledgers (creates a campaign with `template=announcement.ack_reminder`), export; guardians' acks for student announcements when `requires_ack` and audience includes parents.
- `emergency_service.py` (`comms.emergency_broadcast`, `communication:emergency`): one-click broadcast to `all|college|hostel|custom` on **all channels**, bypasses quiet hours/preferences (except legal unsubscribe for marketing — not applicable), highest queue priority (`notifications` queue with priority 9), creates `bulk_campaigns(is_emergency=true)` + links `emergency_alerts` row when raised from an SOS (Phase 25) or a manual incident; confirmation step with typed phrase; incident log (who, when, message, reach) exported for the safety register; follow-up "all clear" message; drill mode (marks `[DRILL]`).
- `bot_service.py` (`comms.whatsapp_bot`)
  1. Webhook (`POST /webhooks/whatsapp/{connection}`; Phase 04 skeleton) → signature verify → `wa_processed_messages` idempotency (UNIQUE `wa_message_id`) → session lookup by phone (`conversation_sessions(channel='whatsapp', external_id=phone)`), identity resolution: phone → `users` (student/guardian/staff) with OTP-less trust when the phone is verified in profile, else `talk_to_human`/link flow.
  2. Flow engine: menu-driven steps from `platform_settings['bot_flows']` (state machine in `conversation_sessions.state`), interactive list/buttons; tools call the same read services with the resolved user’s `Principal` (visibility enforced: a guardian sees only wards); flows: attendance (per course % + shortfall), dues (with pay link → Phase 12 online), timetable (today/tomorrow), results (latest published; masked unless `results.sms_masked_notify` rules), hall ticket link, out-pass status (Phase 20), fee receipt PDF link, complaint (creates service request Phase 25 or grievance Phase 27 when present), talk to human (creates support ticket/notification to office); 24 h session window awareness (outside window → template message first); rate limits; transcript retention 90 days, masked for officers.
  3. Outbound: notifications with `whatsapp` channel reuse the same adapter; bot replies logged in `message_logs(channel='whatsapp', event_type='bot.reply')`.
- `assistant_service.py` (`comms.ai_assistant`)
  1. Opt-in per user (`consent_records` Phase 01 privacy) and `allowed_roles`; provider via `LlmProvider` adapter (mock deterministic in dev/tests; Groq/OpenAI/Azure/Ollama live) with `integration_connections`; **no PII leaves the tenant without `assistant.allow_pii_to_provider`** (default false → tool results are summarised/masked before prompting).
  2. Tools = typed wrappers over read services (my attendance, my dues, my timetable, my results, my leaves/balances, my mentees, department attendance summary for HOD, fee collection today for accountant, policy/FAQ search over `help_articles` and institution policies Phase 33), executed under the caller's `Principal` (permission + visibility) — never with elevated rights; every tool call audited (`audit_logs(action='assistant.tool')`); answers cite the tool/source; write actions are **not** exposed (assistant can only deep-link to the page).
  3. Conversation memory per `conversation_sessions(flow_key='assistant')`, 30-day retention; content filters; token/cost metering to `usage_meters`; admin dashboard of usage and top intents; kill switch (feature flag) instantly disables.
- `simulator_service.py`: dev/demo channel adapters write to an in-memory/Redis inbox per channel; `/comms/simulator/inbox` lists messages (sms/whatsapp/email/push) for QA; can simulate provider delivery/read webhooks and inbound WhatsApp messages to drive bot tests; blocked in production unless `platform_settings['comms.simulator_enabled']`.
- `analytics_service.py`: delivery analytics (sent/delivered/failed/read by channel/template/event/day; failure reasons; cost), provider health (Phase 41 `integration_health_checks` summary + last errors), per-user message history (self), export.
