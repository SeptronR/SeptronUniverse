# PHASE 42 — FLUTTER MOBILE APP (ROLE SHELLS, OFFLINE, DEEP LINKS, QR, PAYMENTS, PRINTING)

## Pre-Requisite
Phases 01–41 complete (the `flutter/` skeleton from `00_PREREQUISITE` §5 exists: pubspec, `l10n.yaml`, `core/*` folders with `screen_registry.dart`, `role_shells.dart`, `deeplinks.dart`, `offline/` stubs; Phase 02 built `features/auth`; Phase 03 the institution/college picker; every phase's **NN.10 Mobile** section lists the screens that phase expects — this phase builds them all against the finished API; Phase 35 supplies `/dashboard` widgets; Phase 39 supplies `/portal/config`, notifications, tours state, help context, association files and push topics; Phase 41 supplies FCM/gateway/SSO connections; `docs/Mobile_App_UI_Structure.md` is the IA contract).

## Objective
Ship the production **Flutter app** (Android + iOS, tablet-aware) that mirrors the web portals and the admin shells for field roles: **core** (Riverpod state, go_router with auth/role/feature/permission redirects, dio client with envelope unwrap/tenant headers/single-flight refresh/Idempotency-Key/retry/`READ_ONLY` handling, secure storage, biometric lock, remote config/force update, theme tokens shared with web + institution branding, 11 locales, FCM + local notifications with deep links, analytics/crash reporting, QR/barcode scanning, Razorpay SDK + UPI intent, ESC/POS thermal printing, PDF viewer/share, image capture with compression), the **role shells** (student, parent, faculty, HOD/dean, registrar/institution admin, COE/exam cell, accountant, HR officer, admissions officer, placement officer, hostel warden/gate staff, librarian, IQAC coordinator, research scholar, alumni, driver, external examiner, recruiter, super admin/support) with bottom tabs + More grid + FABs from `role_shells.dart` and a single `screen_registry.dart`, the **screen set** enumerated in `docs/Mobile_App_UI_Structure.md` §3 and the phases' NN.10 sections (≈ 180 screens grouped in ≈ 45 feature folders), **visibility-aware lists** (`SegmentedScope` from `meta.visibility`), **offline-first** reads (drift cache with TTLs and stale badges) and a **write queue** (attendance marks, GPS pings, gate scans, out-pass decisions, mess attendance, SOS) with idempotent flush and conflict rules, **deep links/universal links** (`/verify`, `/apply`, push payload routes), the shared **widget catalogue** (§4), tablet master-detail layouts, accessibility, structural checks (l10n completeness, no hard-coded strings, golden shells per role, screen-registry coverage against the phase prompts), and store release pipelines (Fastlane/Codemagic, phased rollout) documented for Phase 44.

## Feature keys
`mobile.app` (on, starter — gates `/mobile/config` and app login), `mobile.offline` (on, standard), `mobile.biometric_lock` (on, starter), `mobile.tablet_layout` (on, standard); every screen additionally carries the owning module key (`hasFeature`) and permission (`can`) exactly as its web counterpart; `attendance.qr`, `attendance.geo_app`, `attendance.offline_mobile`, `hostel.gate_qr`, `fees.thermal_receipts`, `facilities.emergency_sos`, `transport.gps_live`, `exams.onscreen_valuation` (mobile read-only for evaluators), `comms.push` are consumed here.

## Visibility rules
Identical to the API: the app never widens or narrows beyond `meta.visibility`. Portal personas (student, parent, alumni, scholar, applicant, recruiter, driver, external examiner) see self/wards/ownership only and no scope control; staff shells render `SegmentedScope` **Mine | Dept | College | All** only from the scopes returned per list; HOD-who-teaches gets the HOD shell with faculty screens under More (self); accountant HR tab shows All staff / All leaves / All staff attendance with a Mine segment; warden sees own hostels; gate staff a 3-tab shell; super admin/support a read-mostly shell; PII masked per `meta.pii` and screenshots blocked on marks/valuation/PII screens; every write goes through the same endpoints with the same permissions (403 → friendly "not allowed" with the reason code).
