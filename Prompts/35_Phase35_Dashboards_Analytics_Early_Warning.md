# PHASE 35 — DASHBOARDS, ANALYTICS & EARLY-WARNING

## Pre-Requisite
Phases 01–34 complete (every module ships a `stats_service` and registers metric computation functions in `app/core/metrics.py` (Phase 32); Phase 27 owns the risk-scoring job `risk_service.compute` that writes `risk_flags`; Phase 01 shipped the `/dashboard` placeholder, `StatCard`, the Recharts wrappers with mandatory table view and the `dashboard:{institution}` WebSocket channel). Phase 36 (reports) reuses this phase's chart providers for exports; Phase 39 renders the portal home pages from the role dashboards; Phase 42 renders the same widgets on mobile Home tabs.

## Objective
Replace every placeholder dashboard with **role dashboards** composed from a **chart registry** (`app/core/charts.py`) and a **dashboard registry** (`app/core/dashboards.py`) — stat cards, charts (with table view), lists and quick actions per role (institution admin/principal, registrar, COE/exam cell, dean, HOD, faculty, class advisor/mentor, student, parent, accountant, HR officer, admissions officer, placement officer, hostel warden, librarian, transport manager, estate officer, IQAC coordinator, research cell/guide/scholar, alumni coordinator, college admin, auditor) — with **drill-down** from any number to the filtered list page under the same visibility, **institution/college/department scope tabs**, **materialized read models** refreshed by Beat and invalidated by domain events (so 50 000-student tenants render dashboards in < 300 ms), **early-warning analytics** on top of Phase 27 risk flags (cohort heat maps, factor trends, intervention tracking, at-risk alerts to mentors/HODs/registrar), KPI targets with threshold alerts, module **Insights tabs** (analytics on any list page), dashboard personalisation (pinned widgets, layout per role editable by institution admins), scheduled dashboard digests (email/WhatsApp via Phase 24) and optional live refresh over WebSocket.

## Feature keys
`core.dashboard` (core; registered in Phase 01 — role dashboards are always on), `analytics.core` (on, standard: chart registry, Insights tabs, drill-down, read models, digests), `analytics.early_warning` (off, professional; depends `analytics.core`; Phase 27's `mentoring.early_warning` depends on it — the scoring job lives in Phase 27, the cohort analytics/alerts live here).

## Visibility rules
Dashboards never widen visibility: a widget renders only when the principal holds the widget's `permission`, and every chart provider queries through `BaseRepository.visible_to(principal, module)`, so the same widget shows department numbers to an HOD, own-offering numbers to faculty, wards to a parent and self to a student. Read models carry `institution_id`, `college_id`, `department_id`, `program_id`, `staff_id`/`enrollment_id` dimensions so the predicate applies to them exactly as to the source tables.
| Role | Dashboard scope | Drill-down | Early-warning |
|---|---|---|---|
| student / parent | **S** / **W** (own numbers only; class average as the only comparison) | own rows | own level only when `risk.show_to_student` (Phase 27 setting) |
| faculty / class_advisor / mentor | **O** (own offerings, advisees, mentees) | own rows | O (mentees) |
| hod / dean | **D** / **F** with ScopeTabs Department \| (Faculty) | department rows | D / F (cohort heat map, acknowledge) |
| registrar / principal / institution_admin | **A** with ScopeTabs Department \| College \| All | all rows | A (institution cohort, interventions, alerts) |
| coe / exam_cell / accountant / hr_officer / admissions_officer / placement_officer / librarian / transport_manager / estate_officer / alumni_coordinator / research_cell | **A** for their module widgets only (`<module>:view_all`) | module rows | — |
| hostel_warden | **H** | residents | H (residents' levels when the `hostel` factor fires) |

- `kpi_service.py`: targets per institution/college (settings), evaluation after each `mv_kpi_daily` refresh → `analytics.kpi_threshold` notifications to `alert_recipients` (once per breach, with a recovery notice), KPI history for trend sparklines, public counters for the Phase 40 website (students, programmes, faculty, placements — only keys listed in `analytics.public_counter_keys`).
- `risk_analytics_service.py` (`analytics.early_warning`)
  1. Cohort views over `mv_risk_cohort`: heat map by department/program/batch/hostel/category × level, factor means (attendance, CIA, dues, standing, hostel, engagement), trend across terms; student lists with filters (level, factor, unacknowledged, no intervention in N days) under Phase 27 visibility (mentor → mentees, HOD → department, registrar → all).
  2.   3. Alerts: after each `risk.computed` — new `high` share per department above `risk.alert_threshold_pct` → `risk.cohort_alert` to HOD/registrar; students `high` on two consecutive computations without an intervention within `risk.intervention_due_days` → `risk.intervention_due` to mentor + HOD; hostel factor high → warden list.
  4. Exports (job): cohort xlsx, student list (PII masked unless `students:view_pii`), IQAC evidence table (aggregates only) for NAAC 2.x/5.x.
